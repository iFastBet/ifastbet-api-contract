# Права по типам узлов — API v8

`contract.json → permissions` — общий каталог для backend и админки. Каждый ключ
описывает действие (`action`), тип цели (`target_type`), раздел (`section`),
допустимые типы получателей (`applies_to`), роли зала (`roles`), зависимости
(`requires`) и область относительно узла сотрудника (`relation`).

## Матрица прав — 18 сентября 2026

Adminka 1.0.38 и PocketBase 0.9.20 сохраняют каталог ключей и форматы API v8.
Последующее описание исходной модели v8 следует читать с уточнениями ниже.

- `structure.view` становится базовым доступом административных пользователей,
  включая менеджера зала, но исключая кассира. Явное назначение ключа больше не
  требуется. Доступ ограничен своей веткой; настройки, пользователи, статистика
  и действия по-прежнему требуют отдельных типизированных прав. После отзыва
  разделов realtime продолжает отдавать только разрешённые метаданные узлов.
- При изменении назначений сохраняемые прежние ключи не нужно выдавать заново.
  Сервер проверяет полномочия выдающего на добавляемые ключи и их зависимости,
  а допустимость уровня/роли — для всего итогового набора. Удалять прежние ключи
  можно, повышать доступ без соответствующих полномочий нельзя. Для создания
  пользователя проверяются все запрошенные назначения.
- UI объединяет права в строки «Структура», «Пользователи», «Валюты», разделы и
  особые права. Просмотр игр отделён от управления, кредитные операции объединены
  в управление, сотрудники залов — в пользователей. Статистика, журнал и ставки
  не имеют режима управления. Ролевые ограничения менеджеров зала сохраняются.
- Частичные назначения сохраняются до явного изменения ячейки; загрузка формы
  и изменение другой ячейки не расширяют доступ. Миграция
  `1789732800_structure_baseline.js` меняет только правила чтения nodes, без
  преобразования назначений и без изменений финансовых данных.

## Назначение и исполнение

Иерархия: `root → dealer → agent → hall`. Сотрудник может получить разрешения
только своего типа и нижестоящих типов. Например, сотруднику агента доступны
`agent.*` и `hall.*`; даже суперагент не может назначить ему `dealer.*`.

Административное разрешение и все его зависимости должны принадлежать выдающему
и быть допустимыми для его уровня и роли. «Включить всё» в форме использует это
же пересечение. Исключение сохранено только для кассовых `cashier.*`: их может
выдать сотрудник с `hall.cashiers.manage`, хотя сам он не является кассиром.

При действии сервер проверяет точный ключ для типа цели, допустимость для роли
и наличие узла сотрудника в `target.path`. Права агента никогда не открывают
соседнего агента. `relation=descendant` исключает собственный узел; `self`
разрешает только собственный; `subtree` включает собственный и потомков.
Создание проверяется на непосредственном родителе нужного типа.

Право просмотра не даёт изменения. Создание и изменение узлов (`dealer.create`,
`agent.update` и т. п.) доступны только вышестоящим сотрудникам. Изменение
пользователей включает удаление; собственная учётная запись редактируется
только через профиль. Менеджер зала может управлять кассирами, но не менеджерами.

## Независимость блоков

- Дашборд и отчёты агента охватывают его ветку по `agent.*`, без прав залов.
  Переход в отдельный зал требует соответствующего `hall.*`.
- Игровые настройки разделены на шаблоны суперагента, доступность игр конкретного
  узла и самостоятельные настройки зала. Управление требует просмотра того же
  типа. `hall.tv.language.manage` самостоятельно открывает только язык зала.
  `root.games.settings.view` позволяет читать валютные шаблоны залов; изменение
  шаблонов требует отдельного `root.games.settings.manage`.
- Доступ к валютам нижестоящего дилера/агента требует просмотра его кредитов.
  У зала валюта фиксирована. Для перевода/возврата выбирается тип нижестоящего
  участника; остаются только непосредственные связи родитель–ребёнок и прежние
  финансовые проверки баланса, точности, идемпотентности и атомарности.
- Безопасность относится к залам; серверы — к суперагенту.
- `*.structure.stats.view` требует `structure.view`, чтобы показатели были
  доступны через дерево. Просмотр кассиров не открывает их финансовые показатели:
  для них отдельно проверяется `hall.structure.stats.view`.
- `structure.view` открывает общее дерево. Показатели и переходы проверяются
  отдельно по типу каждой строки; дерево не даёт доступа к настройкам.

## Каталог узлов и маршруты

`POST /api/nodes/read` принимает необязательные `type`, `section`, `search`,
`parent`. `section` — раздел каталога или `bets` для истории чеков.
Ответ содержит:

- `items`: доступные цели выбранного раздела с учётом поиска и фильтров;
- `nodes`: краткие сведения для навигации, родителей и подписей отчётов.

Каталог не требует `structure.view`. Подписи потомков в отчёте не дают права
открывать их разделы. Чувствительные поля настроек, TV-токен и язык возвращаются
только при соответствующем доступе. Без разрешений остаются только краткие
сведения о собственном узле.

Группы «Суперагент», «Дилеры», «Агенты», «Залы» показываются только в форме
прав пользователя. Левое меню сохраняет привычный единый список разделов для
выбранного узла. Если доступен только нижестоящий тип, пункт раздела открывает
его доступные цели без дополнительных групп в меню.

«Список и настройки» открывает создание и переименование участников,
«Безопасность» — разрешённые действия с паникой зала. При доступе к нескольким
типам участника внутри раздела появляется переключатель доступных типов.
Перевод и возврат загружают разрешённые для операции балансы без требования
выдать право просмотра остальных балансов. Управление валютами агента открывает
каталог его дилера в пределах ветки сотрудника.

В админке `/access/:type/:section` открывает список доступных целей с поиском и
фильтрами; собственный узел открывается сразу. Существующие `/dashboard`,
`/credits`, `/games`, `/users`, `/journal` и `/agents/:id/...` сохраняются.
Новые `/agents/:id/overview` и `/agents/:id/security` используют существующие
операции изменения имени и режима паники. Неизвестные URL остаются 404.

## Актуальность доступа

Custom API проверяет актуальную запись сотрудника на каждом запросе. Правила
коллекций и realtime используют новые ключи; запись авторизации подписчика
обновляется при изменении сотрудника. Клиент получает изменение своей записи,
перезагружает доступную ветку и закрывает запрещённые разделы и действия.
Запрет действует на сервере и для ранее выданного токена.

## Перенос и локальная проверка

### API v8: управление менеджерами

У менеджеров и кассиров зала одинаковое разделение: отдельное право просмотра
и одно право создания, изменения и удаления. `hall.users.manage` требует
`hall.users.view` и доступно только сотрудникам root/dealer/agent для залов
своей ветки. Менеджер зала по-прежнему не управляет другими менеджерами.
Пользователи root/dealer/agent сохраняют отдельные права создания и изменения.

Миграция `1789494000_manager_management.js` заменяет любое из старых
`hall.users.create` / `hall.users.update` на `hall.users.manage` с просмотром.
Это намеренно расширяет прежнее частичное назначение до всех трёх операций.
Пользователи только с просмотром новых операций не получают; остальные права
сохраняются. Ошибочные старые назначения сотрудникам зала удаляются без выдачи
управления. Старые ключи больше не принимаются API.
Для отката нужна резервная копия: исходное разделение прав восстановить нельзя.
Frontend и backend выпускаются согласованно; админку v7 после обновления нужно
перезагрузить. Игровые и финансовые данные перенос не меняет.

### История перехода на типизированные права

Backend-миграция `1789142400_typed_permissions.js` содержит фиксированный снимок
каталога и однократно распределяет прежние широкие права по допустимым типам.
Она сохраняет различие между своими и нижестоящими пользователями, ограничения
ролей и необходимые прежние права для операций. Неполные старые наборы не
получают ранее запрещённых операций. Старые административные ключи не являются
runtime-алиасами; неизвестный ключ отклоняется.

Перед обновлением нужна резервная копия БД. Миграции применяются до загрузки
новых hooks: исторический seed ещё содержит прежние ключи. Откат выполняется
восстановлением БД и предыдущих версий потребителей. Повторное выполнение
преобразования над уже перенесёнными пользователями недопустимо. Старый
одноразовый перенос аккаунтов требует предварительного обновления исходной БД
до v7; молчаливое отбрасывание прежних ключей запрещено.

Миграция `1789394400_permission_followups.js` применяется после v7 и не повторяет
перенос прежних ключей. Она обновляет чтение валют родителя, добавляет зависимость
статистики от дерева в каталог и дополняет только существующие статистические
права ключом `structure.view`. Остальные права сохраняются. Для её отката также
нужна резервная копия БД: позднее нельзя отличить явно выданное дерево от
автоматически добавленной зависимости.

Потребители фиксируют неизменяемый Git tag `v8.0.0` и соответствующий `bun.lock`.
Перед выпуском выполняется `bun run verify` во всех трёх репозиториях.
Порядок обновления: опубликовать контракт, закрепить его в потребителях,
проверить миграцию на копии production-БД, сохранить резервную копию,
выполнить миграции без загрузки новых hooks, запустить backend и опубликовать
админку. Старая админка с ключами v6 несовместима с новой моделью: после
публикации следует обновить открытую страницу. Данные ставок и балансов
не очищаются.

Проверки покрывают уровни получателя и выдающего, соседние ветки, независимые
отчёты, язык как единственное право, кредитные операции, роли, собственную
учётную запись, прямые коллекции, realtime и миграцию без расширения доступа.

- В браузере проверены меню агента без вышестоящих блоков, создание сотрудника,

  страницы языка). Повторное удаление со старым токеном возвращает 403.
